# Production design note

For 10,000 daily requests containing personal information, I would deploy the Spring API and Python retrieval service as separate, private-container workloads in a managed Kubernetes or equivalent managed-container platform, with an authenticated API gateway and a private service network. I would add a durable queue only if the approval integration's latency or availability requires asynchronous processing; the current synchronous assessment flow should not be silently changed.

The first security changes would be real OIDC authentication and tenant authorization, managed secrets, encrypted transport and storage, strict per-tenant document isolation, malware and content-type checks, retention/deletion controls, data minimization, and redacted structured logging. Submitted text and retrieved passages would remain untrusted; model access would be isolated behind an auditable provider adapter with strict output validation and no ability to approve or pay claims. The largest operational risks are sensitive-data leakage, cross-tenant retrieval, slow or undocumented approval dependencies, duplicate submissions, provider timeouts, and inconsistent policy versions. I would add request correlation, bounded timeouts, rate limits, idempotency controls, metrics and alerts, policy-version auditing, and a recovery plan before launch.

Before committing to a delivery date, I would clarify the approval system's API contract, authentication, rate limits, latency/SLA, idempotency and failure semantics; expected document formats and volumes; legal retention and residency rules; tenant and role ownership; policy conflict escalation; human-review workflow; and required availability, auditability, and deletion guarantees. I would also agree on acceptance criteria and the operational owner for failures. A production timeline should follow those answers and a tested integration spike, not assumptions based on this local prototype.
